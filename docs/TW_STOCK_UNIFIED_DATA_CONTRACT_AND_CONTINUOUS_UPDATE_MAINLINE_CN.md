# 台股统一数据合同与持续更新主线文档

## 1. 背景

当前项目已经不只是一次性离线回测，而是一个会持续运行的台股研究与组合策略产品：

- 每天会自动拉取新数据；
- 每天会生成新的 qlib 预测、排名、交叉分析与组合策略建议；
- 前端需要长期展示连续、可解释、可比较的历史与最新结果。

因此，后续所有数据修复、策略训练、LTR 补强、前端展示，都必须建立在一份统一且可持续的数据合同之上。

本主线的核心目标不是“先提高某次回测收益”，而是先确保：

1. 历史数据与未来每日增量数据来源、字段、复权与日历口径一致；
2. `2015-2026` 历史段与后续每天新增数据可无缝拼接；
3. 150 支候选股票的日频数据覆盖稳定、可解释；
4. 后续 qlib / LTR / 排名 / 组合策略都运行在同一份统一数据底座上；
5. 不再反复出现 full/common universe 混乱、年份间口径漂移、旧产物与新产物不可直接比较的问题。

## 2. 主目标

本主线需要冻结一份可长期使用的“台股统一数据合同”，并回答以下问题：

1. 当前 `2015-2026` 的历史数据是否同一口径？
2. 当前每天自动拉取的新数据，是否与历史数据完全同口径、可直接拼接？
3. Yahoo / FinMind / 现有 normalized 数据 / qlib 输入数据之间，哪些是真正的主链路，哪些只是补充链路？
4. 是否能保证 150 支股票在“上市后且可交易期间”内具备稳定完整的日频数据？
5. 是否能为后续 qlib 连续打分、LTR 训练、组合策略生成，提供同一份持续增长的统一数据底座？

## 3. 用户要求

本主线必须满足以下用户要求：

1. 历史数据与未来每天自动更新的数据必须是同一口径、同一规范、可持续拼接；
2. 后续每天拉取数据、生成预测、生成排名和组合策略时，不能因为数据源或数据规范变化导致结果漂移；
3. 原来的历史数据必须能和新数据自然拼接，不能出现“旧数据一套规则、新数据另一套规则”；
4. 必须尽量保证 150 支股票都有完整的每日数据；如果某些日期无法完整，必须明确区分：
   - 上市前；
   - 停牌/无交易；
   - 原始源缺失；
   - 特征窗口不足；
   - label horizon 不足；
   - 其他异常。
5. 之后任何策略比较都应该优先基于统一 universe 进行，不允许再把 coverage 差异混成模型优劣。

## 4. 范围

本主线只包含：

1. `2015-2026` 历史日频数据口径审计；
2. 当前每日自动更新链路的来源、字段、复权、日历、symbol 映射审计；
3. 历史数据与增量数据可拼接性审计；
4. 150 支候选股票的覆盖审计与缺口分类；
5. 统一 full universe / model-ready universe 合同定义；
6. 后续 qlib 连续打分和 LTR 严格补强所需的数据前置合同。

本主线不直接包含：

1. 新策略训练；
2. 新 LTR 回测；
3. 前端改版；
4. accepted latest 切换；
5. provider refresh / publish；
6. 真实交易或任何 broker / order / quick-trade 链路。

## 5. 核心审计对象

### 5.1 原始历史数据

需要确认：

1. `2015-2026` 的原始日频数据来自哪些来源；
2. 不同年份是否混入不同来源或不同字段定义；
3. 复权/调整价规则是否一致；
4. symbol 命名规范是否一致；
5. 交易日历是否一致；
6. 是否存在年份切换时的格式或口径漂移。

### 5.2 当前每日自动更新链路

需要确认：

1. 现在每天自动拉取脚本实际使用哪些数据源；
2. Yahoo 在当前链路中负责什么；
3. FinMind 在当前链路中负责什么；
4. normalized 产物是如何生成的；
5. 新增一天的数据会写入哪里；
6. 新增数据与历史数据是否使用完全一致的字段、复权、symbol、calendar 规则；
7. 若 Yahoo/FinMind 某天失败，是否会产生格式不一致或临时 fallback 造成口径变化。

### 5.3 统一 universe

需要区分两层：

1. `raw full universe`
   - 只要股票在上市后且可交易期间，就应尽量具备完整原始日频数据。

2. `model-ready universe`
   - 在 raw 数据之上，再按固定规则判断某日某股是否具备：
   - 足够历史窗口；
   - 足够未来 horizon；
   - 足够特征完整性；
   - 足够 label 完整性。

后续所有策略比较必须明确自己使用的是哪一层 universe。

## 6. 必须冻结的数据合同

本主线结束后，必须冻结以下合同：

1. 原始日频主数据来源合同；
2. 增量更新主数据来源合同；
3. 复权/adjusted price 合同；
4. symbol 映射合同；
5. TWII / 市场状态辅助数据合同；
6. 交易日历合同；
7. raw full universe 合同；
8. model-ready universe 合同；
9. qlib 连续打分输入数据合同；
10. 后续 LTR 训练输入数据合同。

## 7. 与后续 LTR 严格补强的关系

本主线是后续“严格补强版 LTR”的必要前置条件。

只有当以下条件全部满足，才允许进入下一条 LTR 主线：

1. `2015-2026` 历史数据与当前每日增量数据口径一致；
2. `2021-2025` 可基于统一 frozen qlib 合同连续打分；
3. 150 支股票的 raw/full coverage 已经解释清楚；
4. model-ready 过滤规则已冻结；
5. 不再依赖临时 common/full 口径修补来解释策略优劣。

下一条 LTR 主线应当建立在此基础上：

- 冻结 old qlib；
- 用统一口径连续生成 `2021-2025` qlib score；
- LTR 在统一样本合同上训练；
- 其余特征、label、preserve scope、replay 规则尽量继承第一版。

## 8. 交付物

本主线至少需要输出：

1. 历史数据来源与口径审计报告；
2. 当前自动更新链路来源与拼接性审计报告；
3. 150 支股票覆盖审计与缺口分类报告；
4. 统一 raw full universe 定义；
5. 统一 model-ready universe 定义；
6. “后续 qlib 连续打分 + LTR 严格补强”可执行前置结论。

## 9. Gate

只有满足以下 gate，主线才算通过：

1. 能明确说明当前历史数据和每日增量数据的真实主来源与处理链路；
2. 能明确证明二者可持续拼接，或指出必须修复的具体环节；
3. 能明确区分 raw 缺失、停牌、上市前、窗口不足、label 不足等问题；
4. 能冻结统一 universe 合同；
5. 能为后续 frozen qlib `2021-2025` 连续打分提供稳定数据底座。

推荐 gate：

```text
tw_stock_unified_data_contract_ready_for_strict_ltr_extension
```

## 10. 对执行者的约束

执行者不得：

1. 直接跳过数据合同审计去训练新 LTR；
2. 用临时 common/full 过滤结果包装成最终公平比较；
3. 静默混入不同来源、不同复权、不同日历的历史数据；
4. 修改 accepted latest；
5. 触发 provider refresh / publish；
6. 修改真实前后端业务链路；
7. 输出买卖指令或任何真实交易语义。

## 11. 对审查者的要求

审查者必须重点确认：

1. 历史数据与每日增量数据是否真能长期拼接；
2. 是否把“原始数据不全”和“模型样本过滤”混淆；
3. 是否已经把 full/common universe 混乱问题前置解决；
4. 是否真的为后续 strict LTR extension 建好了统一底座；
5. 若存在关键未知项，必须停止并要求补审，不得放行到下一阶段。
