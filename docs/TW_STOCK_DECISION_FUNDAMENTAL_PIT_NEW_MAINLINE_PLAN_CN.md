# 台股 Decision Model 基本面 PIT 新主线与失败后解释模块路线

## 1. 当前背景

上一条正交数据规则探索主线已经在 Phase2D 收口：

- `orthogonal_rule_exploration_closed=true`
- `manual_rule_cards_frozen=true`
- `phase3_allowed=false`
- `risk_filter_model_training_allowed=false`
- `frontend_api_integration_allowed=false`
- `requires_user_decision_for_new_direction=true`

结论是：法人筹码与融资融券规则有解释价值，但不足以作为模型 gate 或自动风险过滤依据。继续 Phase2E/Phase3 会变成无边界调参和过拟合搜索，因此停止。

本文件定义新的主线，不继承 Phase2D，不继续旧规则搜索。

新主线优先尝试：

> 引入具备 point-in-time 证据的月营收/基本面数据，验证其是否能给 qlib rank 提供稳定信息增量。

如果新主线失败，再整理此前探索得到的稳定解释信息，做人工复盘解释模块。

## 2. 用户第一性原则

所有阶段必须符合：

1. 简单：最终用户看到的是清楚的研究解释，不是复杂字段堆叠。
2. 准确：所有基本面/月营收字段必须严格 point-in-time。
3. 清晰：必须区分“模型增量证据”和“人工解释信息”。
4. 实用：如果不能稳定改善策略或复盘质量，就不产品化为决策模块。

本项目仍然是 research-only：

- 不接 broker。
- 不生成订单。
- 不给目标仓位。
- 不做自动买卖。
- 不给收益承诺或上涨概率承诺。

## 3. 新主线核心假设

旧正交规则主要使用：

- 法人筹码。
- 融资融券。

它们更偏资金流和筹码拥挤，适合解释短期风险，但单独作为规则 gate 不稳定。

新主线尝试加入更正交的基本面信息，优先级如下：

1. 月营收 YoY / MoM。
2. 月营收 YoY 连续改善/转弱。
3. 近 3 个月 YoY 均值和斜率。
4. 公告后天数 `days_since_last_report`。
5. 若可获得且 PIT 可靠，再考虑财报/估值字段。

核心问题：

- qlib Top50 中，月营收持续改善的股票是否未来表现更稳？
- qlib 高排名但月营收转弱的股票是否更容易失败？
- 月营收是否能解释法人/融资融券规则不稳定的区间？
- 基本面确认能否减少高位追入或熊市误选？

## 4. 强制 PIT 原则

月营收/财报类数据必须具备：

- `symbol`
- `source_period`
- `announcement_date`
- `available_at`
- `revenue`
- `yoy`
- `mom`
- `data_source`
- `raw_snapshot_id`
- `days_since_last_report`

禁止：

- 用 `source_period` 直接 join 到当月交易日。
- 用事后修正数据覆盖历史。
- 没有公告日却假设月初或月底可见。
- 为了提高回测结果而补未来值。

如果没有可靠 `announcement_date` / `available_at`，该数据源不得进入 Phase 1。

## 5. 总体路线

### Phase F0：基本面/月营收数据源可行性与 PIT 方案

目标：

- 只读盘点可用数据源和脚本。
- 判断是否能拿到公告日或等价可见时间。
- 设计 raw archive schema。
- 不下载真实数据，不训练模型。

必须回答：

- FinMind 是否有月营收字段及公告日。
- 现有仓库是否有月营收脚本。
- 若无现成脚本，是否需要新增脚本。
- 是否需要联网和 token。
- PIT 归档如何保证不泄漏。

Gate：

- 若找不到可审计公告日/available_at 方案，新主线停止。
- 若方案可行，进入 F0B/F0C 小范围 POC。

### Phase F0B：用户确认后的受限数据 POC

目标：

- 在用户授权后，小范围联网拉取月营收/基本面数据。
- 写入独立 raw archive，不影响 qlib provider、accepted latest 或前端。
- 只验证覆盖率、字段、PIT 可用性。

推荐范围：

- 时间：先 2024-01-01 至 2026-06-11，或先最近 18 个月。
- 股票：qlib Top50/Top150 历史涉及样本，不全市场。
- 数据：优先月营收。

禁止：

- 不 materialize 到 qlib provider。
- 不训练模型。
- 不构建完整 Phase 1 样本。
- 不接前端/API。

Gate：

- 至少有足够 symbol-date 的 PIT-valid rows。
- `announcement_date` / `available_at` 逻辑可审计。
- 覆盖率足够做初步增量检验。

### Phase F1：PIT 样本构建与单因子增量检验

目标：

- 构建 date-symbol 样本。
- 合并 qlib rank、价格/技术、大盘、法人/融资融券已有解释字段、月营收 PIT 字段。
- 只做单因子和分组检验，不训练模型。

必须检验：

- 月营收 YoY 改善 vs 未来 20/60 日超额收益。
- 月营收转弱是否能识别 qlib 高排名失败样本。
- 月营收与 qlib score/rank 的相关性。
- 月营收与法人/融资融券规则是否互补。
- 牛市、震荡、熊市分组表现。

Gate：

- 至少一个基本面特征在多个年份/市场阶段稳定有增量，才允许进入 F2。
- 若只在单一区间有效，不进入规则或模型阶段。

### Phase F2：规则型基本面确认 baseline

目标：

不训练 ML，先做简单可解释规则。

候选规则：

- qlib Top50 + 月营收 YoY 改善 + 无融资拥挤 -> 多源确认。
- qlib Top50 + 月营收连续转弱 -> 谨慎观察。
- qlib Top50 + 法人卖超 + 月营收转弱 -> 持仓复盘。
- qlib Top150 + 月营收强改善 + 法人支持 -> 扩展观察，但不得直接 confirmed。

Gate：

- 规则必须比裸 qlib rank 或旧法人/融资融券规则更稳定。
- 若规则仅有解释意义，不进入模型训练。

### Phase F3：Risk Filter / Fundamental Confirm Model v1

只有 F1/F2 都通过才允许进入。

目标：

- 模型不替代 qlib rank。
- 模型只输出研究状态：
  - `confirmed_watch`
  - `normal_watch`
  - `caution_watch`
  - `defer_watch`
  - `review_existing`

Gate：

- 必须同时超过 qlib baseline 和规则 baseline。
- 必须在多个时间区间稳定。
- 必须可解释。
- 不能牺牲清晰度换取轻微指标提升。

### Phase F4：模拟账户/持仓复盘只读验证

目标：

- 验证新规则/模型是否能改善持仓复盘质量。
- 重点看回撤、换手、误报、漏报，而不是只看收益。

Gate：

- 若增加复杂度但不能明显改善复盘质量，不进入前端。

### Phase F5：前端只读产品化

只有 F4 通过才允许。

前端只显示：

- 基本面确认。
- 基本面转弱。
- 筹码/基本面冲突。
- 人工复盘原因。

禁止：

- 展示复杂训练指标。
- 输出买入/卖出。
- 输出目标仓位。
- 输出收益承诺。

## 6. 失败后路线：人工复盘解释模块

如果新主线在 F0/F1/F2/F3 任一阶段失败，则不继续调参。

失败后整理现有可用信息，做人工复盘解释模块：

### 6.1 可纳入解释的信息

- qlib rank / score / Top30 / Top50。
- QuantDinger trend。
- MA/RSI/MACD/Bollinger 技术状态。
- 价格位置风险。
- 法人/融资融券冻结规则卡：
  - 融资拥挤 caution。
  - 法人/拥挤冲突 review。
  - 外资流向背景解释。
  - 融资变化辅助确认。
- 若月营收只具备解释价值，也可作为“基本面背景”，不得作为自动 gate。

### 6.2 模块定位

模块只回答：

- 为什么这只股票需要人工复盘？
- 哪些信息互相支持？
- 哪些信息互相冲突？
- 哪些风险不应忽略？

模块不回答：

- 是否应该买入。
- 是否应该卖出。
- 买多少。
- 目标仓位。
- 未来收益率。

### 6.3 前端形态

建议作为现有台股研究/模拟账户中的轻量区块，不新增复杂页面：

- 标题：`复盘线索`
- 状态：
  - `多源支持`
  - `信息冲突`
  - `位置偏高`
  - `筹码拥挤`
  - `基本面待确认`
  - `数据不足`
- 每只股票最多显示 3 条最重要原因。

## 7. 执行者与审查者协作机制

继续采用双窗口交替机制。

1. 审查者先给出下一步工作文档。
2. 执行者只执行该文档，不自行扩展。
3. 执行者完成后写执行报告。
4. 审查者审查报告、代码、数据产物、安全边界。
5. 审查者给出“审核意见 + 下一步工作文档”。
6. 若遇到未知问题或需要用户授权，必须停止并问用户。
